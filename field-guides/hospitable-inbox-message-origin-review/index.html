Review Message Origins in the Hospitable Inbox

AI-assisted editorial guide · Published November 20, 2026

Hospitable’s inbox documentation explains the conversation thread and how messages appear, including AI-assisted drafts and connected services. Before relying on a unified inbox, define who is allowed to send which replies and how the team will investigate an unexpected message. A single conversation view does not necessarily identify every sending system without further review.

Decision processChecklistOfficial sources

Map the connected messaging paths

List the booking channels, Hospitable features and third-party tools that can send messages. Identify whether each produces a draft or sends directly. Do not assume the person reading the inbox is the only source of outgoing communication. Keep the list current when software trials or integrations are added to the account.

Read the current display behavior

Use Hospitable’s official inbox guide to understand the labels and information visible in the thread. It notes that some third-party messages can appear like manual replies. Avoid assigning blame or concluding that a staff member sent a message solely from its appearance. Investigate the connected workflow and available records before reaching a conclusion.

Set a review boundary for AI drafts

Decide which topics require human review and who checks the source information used in a reply. An AI-suggested draft sent from a reply box remains a message the operator has chosen to send. Confirm property details, reservation facts and any proposed commitment before sending it. Do not treat fluent wording as proof of accuracy.

Remove competing instructions

Review whether several systems answer the same trigger or guest question. A channel message, scheduled template and connected tool can create contradictory replies even when each seems reasonable alone. Assign a primary workflow for the topic and document exceptions. Disable or adjust a redundant path through the vendor’s authorized controls rather than deleting evidence after a problem.

Prepare an investigation record

For an unexpected reply, preserve the reservation reference, message time and relevant configuration. Limit shared guest information to what the investigation needs. Ask the software provider about available message-origin evidence and retention. Keep a support response separate from assumptions made by the operating team.

Use a conflicting-answer example

Suppose a guest receives two different arrival times. Compare the manual reply, scheduled content and connected tools before correcting the guest-facing information. Then identify which configuration caused the conflict and who will maintain it. A unified inbox is useful only when the team understands the automation behind the visible conversation. Create a short internal response log identifying the confirmed sending path and the correction made. If the source remains unknown, leave it unresolved and ask the provider what evidence is available. Do not manufacture an audit trail from assumptions, and avoid telling a guest that a system was responsible before the team has confirmed the facts.

  • Draft versus direct-send authority
  • Current inbox label meanings
  • Primary workflow and exceptions
  • Message-origin investigation record
